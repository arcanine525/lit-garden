Succeeded twice against the existing stack and twice against the fresh one.

initial application admin was linked by issuer/subject and matched the admin
role. The repeat verified the previous binding without resetting its password.
Service credentials and the initial password came from generated, ignored dev
configuration. The application login flow never uses direct password grants.

$ PLAYWRIGHT_CHANNEL=chrome npm run test:e2e
4 passed (9.6s) against the full local stack. The three auth cases used real
Keycloak test identities and exercised the Vietnamese login/password theme.
Student without email: Keycloak requires UPDATE_PASSWORD, no session or API
access before the required action, then linked role and valid session. Logout
deletes the session, a replay of its opaque cookie fails, and cross-origin
logout is rejected. Teacher: forced change, linked role and expiry block API
and UI. Admin fixture: linked role resolves, with the separate bootstrapped
admin binding also verified. Application DB stores opaque session digests
and expiration/epoch metadata, not passwords or issued provider tokens.

Scope: development OIDC service and local application. The admin account setup
script is an operator action. Production HTTPS, admin MFA/device setup and
live Google authorization are outside this run. The theme follows the T05 login
and password layouts. Pixel comparison against approved baselines is T35.
